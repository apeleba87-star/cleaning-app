# 설계 검토 결과 (1차 검토 반영)

각 항목의 결론과 근거. 반영 위치는 괄호 안 문서.

## 1. 현장당 사진 수 한도 → 고정값 제거, 함수 한 곳에서 결정 ([02](02-data-model.md))

| 방식 | 판단 |
|------|------|
| 트리거에 300장 고정 | ❌ 상업/공장/대형 현장에서 정상 사용이 막힌다. 바꾸려면 migration 필요 |
| 요금제(plans) 테이블부터 설계 | ❌ 요금제가 아직 없다. 과설계 |
| **회사별 값(nullable) + 시스템 기본값, 판단은 함수 1개** | ✅ 채택 |

- 기본값 1000장. 목적은 요금제가 아니라 오류/남용 방지.
- 특정 회사만 올릴 때: `companies.max_photos_per_project` 수정 (운영자만).
- 요금제가 생기면: `plans` 테이블 추가 후 `photo_limit_per_project()` 함수 내부만 수정. 트리거, RLS, 앱 변경 없음.

## 2. 서비스 종류 → code 참조 테이블 ([02](02-data-model.md))

| 방식 | 검색 안정성 | 종류 추가 | 판단 |
|------|-------------|-----------|------|
| 자유 텍스트 | ❌ "입주청소", "입주 청소", "입주" 가 모두 다른 값 | 쉬움 | ❌ |
| Postgres ENUM | ✅ | ❌ migration 필요, 값 삭제/이름 변경 불가, 앱과 강하게 결합 | ❌ |
| **참조 테이블 `service_types(code)` + FK** | ✅ code 고정 | ✅ INSERT 한 줄 | ✅ 채택 |

- `code`(MOVE_IN 등)는 영구 식별자, `label_ko` 는 표시용이라 자유롭게 변경.
- 폐지는 `is_active = false`. 과거 데이터 보존.
- 보충 설명은 `service_type_note` (비공개 취급, 검색에 쓰지 않음).

## 3. 공개 가능한 지역 데이터 → 법정동코드 앞자리 + 이름 스냅샷 ([02](02-data-model.md))

- `projects`: `region_sido_code`(2자리), `region_sigungu_code`(5자리), 각 이름. 공개 가능 범위는 시/군/구까지.
- `project_private_details`: `address_road`(도로명/지번), `address_detail`(동/호수). 비공개.
- 입력: 주소 검색 결과에서 코드와 이름을 자동으로 채운다. 대표의 추가 입력 없음.
- 행정구역 변경: 코드와 **입력 당시 이름**을 함께 저장하므로 과거 기록은 깨지지 않는다. 코드 매핑 테이블과 지역 마스터는 검색 기능을 만들 때 추가 (MVP 제외).
- 공개 경계 주의: 향후 포트폴리오에서 "작은 군 + 정확한 작업일 + 사진" 조합으로 고객 집이 특정될 수 있다. 공개 시 작업일은 월 단위로 낮추는 것을 그때 검토한다.

## 4. 작업 규모 → 지금은 컬럼을 만들지 않고 추가 방법만 확정 ([02](02-data-model.md))

- NULL 허용 컬럼 추가는 즉시 끝나는 작업이라 나중에 추가해도 기존 데이터나 구조에 영향이 없다.
- 이름은 `floor_area` / `floor_area_unit`(`PYEONG`, `SQM`) 제안. `areas`(공간) 테이블과 혼동 방지.
- UI는 선택 입력.

## 5. Report token 저장 방식 → token_hash 저장 + 원문은 대표 폰에만 ([01](01-architecture.md), [02](02-data-model.md))

### 비교

| 관점 | A. 원문 저장 (기존안) | B. 해시 저장 + 원문은 대표 폰에 보관 (채택) | C. 서버 비밀키로 token 재생성 (HMAC) |
|------|----------------------|-----------------------------------------------|--------------------------------------|
| Security | DB 백업·덤프·SQL 화면 노출 시 **살아 있는 모든 고객 링크가 유출**되고 사진까지 열람 가능 | DB가 유출돼도 링크 복원 불가 | DB 유출에 안전. 단 비밀키 유출 시 전체 링크 위조 가능 |
| UX: 같은 링크 다시 보내기 | ✅ 어디서나 가능 | ✅ 같은 폰에서 가능. 폰 교체/앱 재설치 시 "새 링크 만들기" | ✅ 어디서나 가능 |
| Performance | UNIQUE 조회 1회 | sha256 1회 + UNIQUE 조회 1회 (차이 무시 가능) | HMAC 검증 1회 |
| 구현 복잡성 | 가장 단순 | 거의 같음: DB에서 `digest()` 1줄, 앱에서 보안 저장소 1곳 | 높음: 비밀키를 Vercel과 DB 양쪽에 관리, 키 교체 시 모든 링크 무효 |

### 결론: B 채택

- `create_report_share` 가 원문을 **응답에서 한 번만** 돌려주고, DB에는 `sha256(token)` 만 저장한다.
- 앱은 원문을 기기 보안 저장소(예: `flutter_secure_storage`)에 `share_id` 별로 보관한다. "링크 다시 보내기"는 여기서 읽는다.
- 원문이 기기에 없으면(폰 교체, 재설치) 앱이 "새 링크 만들기"를 안내한다. 이전 링크는 폐기하지 않는 한 계속 열리며, 공유 링크 목록(생성일, 조회수)에서 폐기할 수 있다.
- 추가되는 구현은 DB 함수 1줄과 앱 저장소 1곳뿐이라 과설계가 아니다. MVP 사용자가 대표 1인·폰 1대라 UX 손실도 작다.
- C는 비밀키 관리와 교체 부담이 커서 제외.

## 6. 비용 시뮬레이션 → 20 / 50 / 100 / 200장 4개 시나리오로 재계산 ([04](04-checklists.md))

- 200장 시나리오에서 10,000개 업체면 1년 누적 Storage가 약 130TB. **Storage 보관기간 정책이 가장 중요한 비용 결정**이 된다.
- 썸네일 전략이 없으면 Egress가 약 5.5배로 늘어난다.
- 사진이 많은 현장을 위해 고객 Report를 페이지 단위로 불러오도록 변경 ([01](01-architecture.md)).

## 7. 핵심 계층 유지

`Company → Project → Area → PhotoPair → MediaAsset` 는 변경 없음. 이번 변경은 모두 다음 중 하나다.

- `companies` 컬럼 추가: `max_photos_per_project`
- `projects` 컬럼 추가: `service_type_code`, `service_type_note`, `region_*`
- `project_private_details` 컬럼 분리: `address_road`, `address_detail`
- 참조 테이블 추가: `service_types` (계층 밖)
- `report_shares` 컬럼 변경: `token` → `token_hash`

## 8. MVP 범위

여전히 구현하지 않음: 포트폴리오, 소비자 탐색/검색, 문의, 견적, 결제, 리뷰, 요금제, 지역 마스터/매핑 테이블, 작업 규모 컬럼, 직원 계정.

이번에 **지금 만드는 것**은 나중에 바꾸기 어려운 데이터 형식뿐이다: 서비스 종류 code, 지역 코드, 한도 판단 함수, token 해시.
